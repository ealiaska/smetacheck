# СверкаСмет

MVP для экспертной проверки двух независимых типов риска в строительных документах:

1. семантически похожие позиции работ с возможными расхождениями единицы, объёма или цены;
2. конфликты БИН, юридического адреса и платёжных реквизитов контрагента между документами.

Система ничего не удаляет, не объединяет и не блокирует. Каждый результат — только предложение для человека; эксперт подтверждает или отклоняет его в интерфейсе. Решения и журнал аудита сохраняются в локальной SQLite-базе.

В репозитории также находится web-версия для Cloudflare Workers: React-интерфейс, HTTP API и постоянный журнал решений в Cloudflare D1.

Production: [https://smetacheck.alaid.workers.dev](https://smetacheck.alaid.workers.dev)

## Web-версия для Cloudflare

Требуется Node.js 20+ и pnpm.

```powershell
pnpm install
pnpm build
pnpm exec wrangler d1 migrations apply smetacheck-db --local
pnpm exec wrangler dev --local
```

Основные API-маршруты:

- `GET /api/health` — состояние Worker и bindings;
- `GET /api/cases?type=estimate|requisite` — контрольные случаи и состояние согласования;
- `POST /api/decisions` — append-only решение эксперта или контролёра;
- `GET /api/registry/{bin}` — проверка регистрации юридического лица по официальному API КГД МФ РК;
- `POST /api/analyze/estimates` — semantic + numeric анализ нормализованных позиций;
- `POST /api/analyze/requisites` — анализ конфликтов реквизитов.

Web-импорт не требует исходного шаблона. Для CSV/XLS/XLSX он:

1. просматривает первые 60 строк каждого листа и находит фактическую строку заголовков;
2. распознаёт русские, казахские и английские варианты названий колонок;
3. при отсутствии узнаваемых заголовков определяет описание, единицу, код и числовые поля по содержимому;
4. пропускает титульные листы, пустые строки и итоги;
5. восстанавливает отсутствующие `document_id`, `page_or_sheet` и `position_id` из имени файла, листа и номера строки;
6. показывает пользователю отчёт «Как распознана структура» перед экспертной работой с результатами.

Таким образом, внутренний API по-прежнему получает стабильную каноническую схему, но входной Excel/CSV может иметь произвольный порядок колонок, титульные строки и привычные названия из смет или АВР.

Для production сначала создаётся D1-база `smetacheck-db`, её `database_id` записывается в `wrangler.jsonc`, затем применяются миграции и выполняется `wrangler deploy`. Токен КГД и другие ключи добавляются только через Cloudflare Secrets и никогда не коммитятся.

## Запуск

Требуется Python 3.11+.

```powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
streamlit run app/streamlit_app.py
```

Приложение сразу открывает синтетические демонстрационные файлы. Во вкладке «Позиции работ» можно загрузить один или два CSV/XLS/XLSX без приведения к шаблону, во вкладке «Реквизиты контрагентов» — один реестр в тех же форматах.

## Архитектура

Основной трек следует фиксированному порядку:

`ingest` → `normalize` → `embeddings` → `numeric_check` + `false_positive_filter` → Streamlit UI.

- `pipeline/ingest.py` валидирует обязательные поля и числа, поддерживает CSV и XLSX.
- `pipeline/normalize.py` приводит текст, синонимы и единицы к каноническому виду.
- `pipeline/embeddings.py` строит локальные multilingual sentence embeddings. Если модель ещё не находится в локальном кэше, `auto` безопасно переключается на word+character TF-IDF; интерфейс `get_embeddings(texts)` остаётся тем же.
- `pipeline/numeric_check.py` сравнивает категорию единицы, объём и цену с порогом 15%.
- `pipeline/false_positive_filter.py` применяет fuzzy-проверку, совместимость единиц и конфликт технических квалификаторов.
- `pipeline/requisites_check.py` отдельно сопоставляет структурированные реквизиты и ранжирует расхождения от `info` до `critical`.
- `pipeline/registry_providers.py` изолирует интеграции с реестрами: по умолчанию сеть отключена, для демо доступен только синтетический mock, а корпоративный HTTPS-шлюз появляется после настройки `REGISTRY_BASE_URL` и `REGISTRY_TOKEN`.
- `pipeline/storage.py` хранит решения и неизменяемые события аудита; optimistic locking защищает от незаметной перезаписи параллельным пользователем.
- `app/streamlit_app.py` показывает таблицу, исходное расположение обеих записей, объяснение и постоянную историю решений эксперта.

Никакие документы не отправляются во внешние AI API. Модель эмбеддингов запускается локально; fallback также полностью локальный. В решение записываются backend, модель, ревизия, размерность и порог, поэтому результат воспроизводим. Синтетические данные не содержат реальных названий компаний, людей, БИН, БИК, счетов или адресов.

## Согласование и постоянное хранение

- Обычное предложение подтверждается одной ролью.
- Для `critical` нужны два независимых подтверждения: `Эксперт` и `Финансовый контролёр`.
- Отклонение любой из ролей переводит результат в состояние «Отклонено экспертом».
- Каждое действие добавляется новой строкой; предыдущие решения не перезаписываются.
- База по умолчанию создаётся в `.data/review.db`. Для тестов или отдельного окружения путь задаётся через `REVIEW_DB_PATH`.

Роли в MVP выбираются в боковой панели. В промышленной версии этот контекст должен поступать из корпоративного SSO, а не выбираться пользователем вручную.

## Интеграция с КГД МФ РК

Web-версия использует документированный endpoint КГД `GET /services/isnaportalsync/public/taxpayer-data` с параметрами `taxpayerCode`, `taxpayerType=UL` и `print=false`. Ответ КГД преобразуется в стабильную схему MVP: БИН, зарегистрированное наименование, тип, статус и даты регистрации/прекращения. Банковский счёт, БИК и юридический адрес этот сервис не подтверждает.

Для автоматического запроса нужен заголовок `X-Portal-Token`. Токен выдаёт администратор КГД после обращения; хранить его следует только как зашифрованный секрет Worker:

```powershell
pnpm exec wrangler secret put KGD_PORTAL_TOKEN
pnpm exec wrangler deploy --minify
```

Значение токена нельзя добавлять в `wrangler.jsonc`, `.dev.vars`, журнал команд или GitHub. Пока секрет не задан, `/api/registry/{bin}` возвращает контролируемый статус `503` и официальный адрес ручной проверки. Синтетический демонстрационный БИН интерфейс никогда не отправляет в государственный реестр. Публичный endpoint ограничен 20 запросами в минуту и принимает браузерный вызов только с того же origin; перед промышленным использованием рекомендуется дополнительно закрыть приложение Cloudflare Access/корпоративным SSO.

## Демонстрация false-positive фильтра

В данных намеренно есть ловушка: «Прокладка силового кабеля…» и «Монтаж оптического кабеля…». Тексты лексически близки и имеют одинаковую единицу длины, но технические признаки `силовой` и `оптический` несовместимы. Пара сохраняется только как `excluded` с причиной и **не предлагается как дубль**.

В реестре есть отдельная ловушка: «Кварц Строй Альфа» и «Кварц Строй Альянс». Названия похожи, но БИН различаются; fuzzy-сходство не используется для автоматического объединения при разных БИН, поэтому межфирменный конфликт не создаётся.

Проверить обе ловушки и остальные критерии:

```powershell
$env:ESTIMATE_EMBEDDING_BACKEND = "tfidf"
pytest -q
```

## Демонстрационные сценарии

- минимум шесть смысловых пар RU/KZ, включая кабель, стяжку, окраску, радиаторы и светильники;
- расхождение количества и цены выше 15% для силовой кабельной линии;
- критичный конфликт: совпадают имя и БИН, но в счёте изменены банк, БИК и ИИК;
- высокий конфликт: точное имя при другом БИН;
- средний конфликт: совпадают имя и БИН, но изменён юридический адрес;
- чистые контрагенты без флагов и две описанные выше ловушки.

## Ограничения MVP

- адаптер официального API КГД реализован, но автоматические запросы недоступны без выданного КГД `X-Portal-Token`;
- API КГД подтверждает регистрационные данные налогоплательщика, но не банковские реквизиты и не юридическую надёжность контрагента;
- нет автоматического юридического или финансового решения;
- TF-IDF fallback менее силён на свободных межъязыковых формулировках, чем локальная neural-модель;
- SQLite подходит для пилота на одном узле; для нескольких инстансов следует заменить его PostgreSQL при сохранении интерфейса `DecisionStore`.
- Web-импорт адаптирован к произвольным табличным сметам и АВР, но PDF, изображения и сканы требуют отдельного OCR/табличного распознавания; обещать безошибочный разбор любого визуального документа без проверки человеком нельзя.
